**Java/C++ generic-type syntax needs `<`/`>` escaped as `&lt;`/`&gt;`** in seeded chapter content, on top of the existing backtick/template-literal escaping rules — unescaped angle brackets in code samples like `ArrayList<String>` or `std::unique_ptr<int>` (or comparison operators like `i < 5`) get misparsed as literal (unknown) HTML tags by the browser and silently dropped, unlike safely-inert prose text. C++'s `<<` stream-insertion operator (`std::cout << x`) needs the same treatment. This wasn't an issue for JavaScript/HTML/CSS/Python content, which rarely uses bare angle brackets in example code.

**Chapter content is authored externally and pasted in as Markdown**, not written directly into `seedChapters.js` — expect a recurring encoding issue when that happens: em dashes, the 💡 emoji, ×, ©, and even multi-byte emoji (e.g. ⭐) all tend to arrive corrupted, almost always collapsing down to a bare "â" (sometimes "Â" or "Ã" for other characters) regardless of what the original character actually was. **Don't blanket-replace every "â" with an em dash** — the correct reconstruction depends on context and has turned out to be, in order of frequency: an em dash (by far the most common — prose asides, comment connectors); a right arrow "→" (nesting/flow chains like `<table>` → `<tr>` → `<td>`, or a decorative "external link" icon); a ✅/❌ pair marking a good/bad code example (established first in the JS Functions chapter's naming-convention comment, reused since — check whether the "â" sits right before a short label word like "Avoid"/"Better"/"Vague" rather than mid-sentence); or, in a numeric/tag range like "0-255" or "h1-h6", a plain hyphen (matching how unambiguous ranges elsewhere in the same file are already written, not an em dash). Compare against how the same construct already reads elsewhere in the file whenever genuinely unsure, and re-verify per new chapter rather than assuming last chapter's mix of cases still holds. Also worth remembering: **topic subdocuments get fresh `_id`s whenever a chapter's `topics` array is replaced wholesale** (as opposed to editing an existing topic in place) — since `Question`/`Progress` reference a topic by that `_id` (see `models/Question.js`/`models/Progress.js` below), replacing a chapter's topics orphans any existing quiz content for it. There's no automatic cleanup for this; after a wholesale topic replacement, query for `Question`/`Progress` docs whose `topicId` no longer matches any current topic in that chapter and delete them (exactly what happened when Loops' topics were replaced — see above).

## Architecture

**Stack:** Node.js/Express backend, MongoDB via Mongoose, vanilla JS + HTML + Tailwind v4 frontend built with Vite, session-based auth (`express-session` + `connect-mongo`), Markdown lesson content rendered with `marked` + `@tailwindcss/typography`.

**Build model is build-only, not dev-server-proxied**: Vite has no dev-server/proxy role in production. `npm run build` compiles `src/` to `codepilot/dist/`, and `server.js` serves that folder via `express.static(path.join(__dirname, 'dist'))` plus a catch-all fallback to `dist/index.html`. During active frontend work, run `npm run dev` (Vite watch, hot reload) in one terminal; `node server.js` only reflects changes after a rebuild, since it just serves whatever is currently in `dist/`. There is no CORS/proxy config anywhere in this stack — don't add one.

**Backend layout** (routes → controllers → models, standard Express pattern):
- `config/db.js` — `connectDB()`, called once in `server.js` before `app.listen`
- `middleware/session.js` — configured `express-session` instance backed by `connect-mongo` (sessions persist in MongoDB, not in-memory)
- `models/User.js` — email, `passwordHash`, name, `languagesToLearn`, `points`, `hasCompletedOnboarding`, timestamps. Password hashing happens in the auth controller (bcrypt, 10 salt rounds), not the model. Has a `toPublicJSON()` instance method — the single place a user gets serialized for a response, so `passwordHash` never leaks; both `authController.js` and `userController.js` call it rather than each having their own copy.
- `middleware/requireAuth.js` — gates a route on `req.session.userId` existing; 401s otherwise. Mount it per-route (see `routes/userRoutes.js`), not globally.
- `routes/authRoutes.js` + `controllers/authController.js` — `POST /api/auth/register`, `/login`, `/logout`. Login regenerates the session (fixation protection) before setting `req.session.userId`. Register does **not** auto-login — it only creates the account, matching the plan's manual test flow (register → login → protected route → logout). Errors from `express-session` callbacks are handled with `res.status(500)` directly rather than thrown, since a throw inside a Node-style callback isn't part of the route handler's promise chain and would crash the process instead of reaching Express's error handling.
- `routes/userRoutes.js` + `controllers/userController.js` — `GET`/`PUT /api/users/me`, both behind `requireAuth`. This used to live at `/api/auth/me` (Phase 2's stand-in "protected route" for testing) but was moved here in Phase 3 since it's really a user-resource concern, not an auth concern — don't recreate a `/api/auth/me`. `PUT` accepts `languagesToLearn` (validated against `shared/languages.js`) and an optional `completeOnboarding: true`, which is the only way `hasCompletedOnboarding` ever flips to true — the settings-page version of this same call never sends that flag, so it can't accidentally un-flip anything (there's no way to set it back to false, by design).
- `shared/languages.js` — `SUPPORTED_LANGUAGES` (objects: `name`, `glyph`, `color`, `chapters`, `topics`) and `LANGUAGE_NAMES` (derived string array used for backend validation). No dependencies either side, imported by both `userController.js` and `src/main.js` so frontend/backend can't drift. **The `chapters`/`topics` counts are real**, as of 2026-08-28 — verified directly against the live database (not just `seedChapters.js`'s source) and updated to match: JavaScript 13/66, HTML & CSS 12/50, Java 10/23, Python 9/19, C++ 9/16, SQL 7/14, Go 0/0, Rust 0/0 (chapters/topics). Nothing keeps this list in sync with the database automatically — re-verify by counting `Chapter`/`topics` in Mongo any time `seedChapters.js` changes, don't just trust these numbers indefinitely.
- `models/Chapter.js` — one `Chapter` document per (language, chapter), with an **embedded array of `Topic` subdocuments** (not a separate collection/model — a chapter's topics are always fetched together, so there's no case where a topic needs independent querying). `language` is validated against `LANGUAGE_NAMES`. Each topic has Markdown `content`, rendered client-side with `marked` + the `@tailwindcss/typography` `prose` class (registered via `@plugin "@tailwindcss/typography";` in `style.css` — Tailwind v4 uses a CSS directive, not a JS config file). A chapter's own `slug` only needs to be unique within its `language` (compound index, so e.g. JavaScript and HTML & CSS can each have their own "Basics" chapter without colliding).
- `controllers/courseController.js` + `routes/courseRoutes.js` — `GET /api/courses/:language` (sidebar tree: chapters + topics with `content` stripped via `.select('-topics.content')`) and `GET /api/courses/:language/:chapterSlug/:topicSlug` (one topic's full content). Both behind `requireAuth`. Mongoose sorts the top-level chapter query but **not** embedded array elements, so topics are sorted by their `order` field manually in the controller before responding.
- `scripts/seedChapters.js` (`npm run seed`) — upserts real course content by `(language, slug)`, safe to re-run. Currently seeds six languages' worth of real chapters: **JavaScript** (13 chapters / 66 topics — JS Basics, JS Operators, JS Functions, JS Arrays, Loops, JS Objects, JS DOM Manipulation, JS Scope & Closures, JS Error Handling, Asynchronous JavaScript, JS Classes & OOP, Modern JS Features, JS Modules & JSON), **HTML & CSS** (12 chapters / 50 topics — HTML Basics, HTML Forms, HTML Tables, Semantic HTML & Embedded Media, HTML Containers/Entities & Accessibility, CSS Basics, CSS Box Model, CSS Colors & Typography, CSS Flexbox, CSS Grid, Responsive Design & Animations, CSS Advanced Selectors & Effects), **Java** (10 chapters / 23 topics — Java Basics, Java Operators, Control Flow, Java Loops, Methods, Arrays, OOP: Classes & Objects, OOP: Inheritance & Polymorphism, Exception Handling, Collections), **Python** (9 chapters / 19 topics — Python Basics, Python Operators & Control Flow, Python Loops, Functions, Lists & Tuples, Dictionaries & Sets, Python String Manipulation, OOP in Python, Python Error Handling & File I/O), **C++** (9 chapters / 16 topics — C++ Basics, C++ Operators & Control Flow, C++ Loops, C++ Functions, C++ Arrays & Strings, Pointers & References, OOP: Classes & Objects, OOP: Inheritance & Polymorphism, Memory Management), and **SQL** (7 chapters / 14 topics — SQL Basics, Filtering & Sorting, Aggregate Functions & GROUP BY, SQL Joins, Data Modification, Table Creation & Constraints, Subqueries & Advanced SQL), all in the order listed. This is the pattern to follow for adding more chapters/languages (Go and Rust remain) — write real accurate content, not placeholder text. **Replacing an existing chapter's `topics` array wholesale (rather than editing a topic in place) generates new subdocument `_id`s** — see the Question/Progress orphaning note above; the Loops chapter has been through this once already (its original 6 topics were replaced with a different 5-topic breakdown). **Chapters with template-literal example code (e.g. Modern JS Features' `${ }` interpolation syntax) need their content escaped twice over** — once for the literal backticks (any chapter with inline-code snippets already needs this), and separately for any literal `${` sequences, or the outer JS template literal in this file will try to actually interpolate them at seed time. The conversion tooling used to build these chapters handles both automatically; don't hand-author a chapter with unescaped `${` in it.
- `shared/judge0Languages.js` — maps our language names to Judge0's numeric `language_id`. **`HTML & CSS` is deliberately excluded** — it has no "run and print output" execution model, so it's not a candidate for the Run button (the execute endpoint 400s if asked to run it).
- `controllers/executeController.js` + `routes/executeRoutes.js` — `POST /api/execute`, behind `requireAuth`. Relays `{code, language}` to Judge0 CE via RapidAPI (`JUDGE0_API_KEY`/`JUDGE0_HOST` in `.env`, never exposed to the frontend) using synchronous mode (`wait=true` — one request/response, no polling) and returns `{stdout, stderr, compileOutput, status, time, memory}`. Judge0's free RapidAPI tier is ~50 executions/day — fine for development/demo, not for classroom-scale usage.
- `models/Question.js` — its own collection (not embedded in `Chapter`), since the adaptive engine queries by topic+difficulty across whatever's currently relevant, not "everything for this chapter" the way the sidebar does. Fields: `language`, `chapterSlug`, `topicId` (a topic subdocument's own `_id` — there's no standalone `Topic` model to `populate()` from), `difficulty` (`easy`/`medium`/`hard`), `type` (`'multiple-choice' | 'code-based'` — the enum exists from day one, but every seeded question today is multiple-choice; code-based questions are planned for the medium/hard bands once the MC path is verified, reusing Judge0 from Phase 5 for execution/grading), `questionText`, `choices`/`correctChoice`, `explanation`, `hint`.
- `models/Progress.js` — one document per `(user, topic)`, a compound unique index on `{user, topicId}`. This is the adaptive engine's entire memory of how a user is doing on a topic: `currentBand`, `correctStreak` (3 in a row bumps the band up; any wrong answer drops it down), `recentQuestionIds` (avoids immediately repeating a question), plus three fields scoped to the *current* practice round — `sessionQuestionsAnswered`, `sessionRawPoints`, `sessionPenaltyPercent` — all reset to 0 once a round banks. Denormalizes `language`/`chapterSlug`/`topicSlug` onto the document itself specifically to avoid having to query `Chapter.topics` just to know what a Progress row is even about. A separate collection rather than embedded on `User`, unlike `languagesToLearn` — progress is written on every single answer and only ever touched one topic at a time, never fetched "all at once" the way a chapter's topics are.
- `controllers/quizController.js` + `routes/quizRoutes.js` — all behind `requireAuth`, all under `/api/quiz`:
  - `GET /:language/:chapterSlug/:topicSlug/next` — upserts the user's `Progress` doc (starts at `easy`) and returns one random question from whichever band it currently says, excluding `recentQuestionIds` (falls back to including them if a band's pool is too small to avoid repeats entirely).
  - `POST /:language/:chapterSlug/:topicSlug/answer` — grades the answer, updates streak/band, and awards points: each correct answer adds that question's band value (`easy=10, medium=20, hard=40`) to the round's raw-points tally; each *wrong* answer adds 10 percentage points to the round's penalty tracker (flat/additive, capped at 100%). Once `sessionQuestionsAnswered` hits the fixed cap of 10, the round banks: `banked = round(rawPoints × (1 − penalty%))` is added to the existing `User.points` field (no new lifetime-total storage needed) and the session trackers reset to 0.
  - `POST /:language/:chapterSlug/:topicSlug/hint` — returns the question's `hint` text and applies the *same* 10-point penalty hit as a wrong answer, against the round's ceiling only (never against points already banked).
  - `GET /:language/progress` — bulk-fetches every `Progress` doc for that language in one call, keyed by `chapterSlug/topicSlug`, so the sidebar tree and the Quiz collection page can each render every topic's status without one request per topic.
- `scripts/seedQuestions.js` (`npm run seed:questions`) — parses Markdown quiz files out of `scripts/question-content/` and seeds the real multiple-choice question bank from them; safe to re-run (deletes and reinserts each topic's questions rather than diffing). One `.md` file covers a whole chapter, named `{chapterSlug}-chapter-quiz.md` (chapter slugs are unique across the whole app, so no language segment is needed in the filename). Inside, `## Topic N: <title>` sections are matched to the chapter's Nth topic **by position** (sorted by each topic's `order` field), not by title text — the MD's topic titles are free-form descriptions, not required to match the seeded topic title. Each topic section has `### Easy` / `### Medium` / `### Hard` subheadings, each with 10 numbered questions (numbering restarts at 1 per topic) laid out as a stem line, four `A)`–`D)` choice lines, and **Hint:**/**Answer:**/**Explanation:** marker lines — the three markers can appear in any order and with or without bold asterisks, and inline code backticks are stripped from all text fields (the quiz UI renders this text escaped-but-plain, not through a Markdown pass, so raw backticks would show up literally). A file doesn't need to cover every topic in its chapter — only the topics it includes get (re)seeded; a topic that already has questions and isn't in the new file is left untouched. Question content arrives incrementally (one chapter file at a time, sent externally) — see the top of the current state section for what's actually been seeded so far.
- `server.js` — wires it all together: JSON parsing, session middleware, static file serving, `/api/auth`, `/api/users`, `/api/courses`, `/api/execute`, `/api/quiz`, `/api/shop`, `/api/profile`, and `/api/home` routes, then the SPA catch-all.
- Frontend (`src/main.js`, `src/api.js`, `src/icons.js`, `src/theme.js`) — a single-state vanilla-JS view that re-renders `#app` innerHTML on every state change and calls the API via `fetch` (same-origin, so the session cookie rides along with no extra config). Screen shown is derived from state + a minimal hand-rolled URL router (no library): no user → auth page (login/register); user but `!hasCompletedOnboarding` → the first-login language-selection gate; user + path `/languages` → the language-management page; user + path under `/course/...` → the lesson page; user + path `/playground` → the Playground; user + path `/cosmetics` → the Cosmetics buy-page; user + path `/profile` → the Profile page; user + path `/quiz` → the Quiz collection; user + path under `/quiz/...` (language/chapterSlug/topicSlug) → the quiz-taking session; otherwise → dashboard. Dashboard, languages, course, Playground, and quiz pages all render through one shared `renderAppShell()` (persistent left sidebar + topbar) — the sidebar **is** the course navigation (expand a track to lazily fetch its chapters, click a topic to navigate). `src/icons.js` is hand-rolled inline SVGs (no icon library dependency for the handful used). `src/theme.js` toggles a `.theme-parchment` class on `<html>` (light theme; dark is the unclassed default), persisted to `localStorage`, read by CSS custom properties in `src/tokens/colors.css` — a full semantic token system (`--fill-accent` vs `--border-accent` vs `--text-link` are deliberately separate roles that diverge in light mode, not aliases) plus `--ondark-*` fixed tokens for surfaces that stay dark in both themes (the brand panel, the code sample — using regular swapping tokens there would mean light mode hands you near-black-on-near-black text). The topbar's points and streak pills both show **real** `user.points`/`user.currentStreak` (kept in sync client-side whenever a quiz round banks, a topic is first viewed, or a shop action fires — no refetch needed), and the avatar slot renders a real DiceBear `<img>` once `user.avatarSeed`/`user.avatarStyle` are both set (falling back to the initial-letter circle otherwise, or on image load failure). The "18,400 students" stat, "Continue with GitHub" button, "Forgot password?" link, and the Playground's Share button are still **visual only**; clicking any of them shows an inline "not available yet" message rather than silently pretending to work. The sidebar's "Explore tracks" item (an inert placeholder with no click handler at all, same category as the above) was removed outright rather than kept as a dead button, since it didn't lead anywhere and had no near-term plan to. The login/register password fields both have a show/hide eye-icon toggle, sharing one generic handler (`.toggle-password-visibility` class, looks up the input via `previousElementSibling` rather than a hardcoded id) — add the same two-element pattern (`.input-wrap` > password `input` + toggle `button`) to any future password field and it picks up the behavior for free. Registering successfully carries the just-entered email/password over to the login form it redirects to (module-level `prefillLoginEmail`/`prefillLoginPassword`, consumed and cleared the first time `renderLoginForm()` runs after) so the user isn't retyping what they just typed — a later, unrelated visit to login starts blank again.
- **Languages page** (`/languages` route) — a dedicated page for managing which languages appear on the sidebar, separate from the first-login onboarding gate (`renderLangGrid`/`bindLangGrid` are shared between the two). Reachable from the sidebar's "Add a language" button and from the Playground's "Add another" link. Diffs the staged `selectedLanguages` array against the saved `user.languagesToLearn` to render a pending-changes bar (add/remove chips, Reset, Save) before anything is actually persisted via `PUT /api/users/me`.
- **Onboarding is a 2-step flow** (`renderOnboardingPage()` in `main.js` is now a thin dispatcher on module-level `onboardingStep`, not a single-screen render): step 1 (`renderOnboardingAvatarStep()`) is a free starter-avatar pick — 3 fixed styles (Bot/`bottts`, Adventurer/`adventurer`, Notionist/`notionists`), each with a hardcoded seed (`'starter'`) so the picker preview is deterministic rather than reflecting a real random pull, unlike the paid Cosmetics-page randomizer. - **Playground** (`/playground` route in `main.js`) — one CodeMirror 6 (`codemirror` + `@codemirror/lang-*` packages; Go/Rust use `@codemirror/legacy-modes` since they don't have first-party CM6 grammars yet) editor instance, language-switching by fully remounting the editor with a different language extension (not a `Compartment` reconfigure — simpler for now, revisit if remounting ever loses meaningful editor state). Output rendering (`renderExecutionOutput`) is shared with the mini playground below, since both hit the same `/api/execute` shape.
- **Mini playground** — a small floating CodeMirror scratchpad, opened via the "Try it yourself" button that lives in the shared topbar (so it's reachable from *any* page, not just `/playground`). Its open/expanded state lives in module-level variables (`miniPlaygroundOpen`/`miniPlaygroundExpanded`), not per-page state, so it survives navigating to a different page while open. Rendered as part of `renderAppShell()`'s output and (re)mounted in `bindAppShell()`, since every page's render fully replaces `#app`.
- **Quiz collection + quiz session** (`/quiz` and `/quiz/:language/:chapterSlug/:topicSlug` routes) — the frontend half of the adaptive quiz system described under `models/Progress.js` above. The collection page lists every topic across the user's selected languages with a real status pill (Not started / In progress · `<band>` / Mastered — "mastered" means the `hard` band was reached, there's no separate discrete "completed" state) and real summary stats (topics practiced / total, points banked from `user.points`) — no fabricated completion percentages. The session page shows one question at a time with a 10-segment progress bar (`Question N of 10`, matching the backend's fixed session cap), a difficulty pill reflecting the *current* band (which can change between questions — that's the adaptive part), a running points/penalty readout, an optional hint, and a round-complete screen once the cap is hit. The sidebar's per-topic status icon (`.topic-status` in the course tree) is driven by the same bulk `GET /api/quiz/:language/progress` call, fetched alongside chapters whenever a track expands.
- **Phase 8 (Points System) — built end-to-end, then reworked into a Profile/Cosmetics split.** `models/Cosmetic.js` is its own collection (like `Question`). Global catalog items (`owner: null`, seeded via `scripts/seedCosmetics.js`/`npm run seed:cosmetics`, upsert-safe by `name`) span 3 purchasable types (`shared/cosmeticTypes.js`'s `COSMETIC_TYPES`): `background`/`border` recolor a glow/ring around the user's avatar, `theme` recolors the Playground's code editor. A 4th type, `avatar`, is never seeded/purchased individually — each one is created on-demand, owned by whoever pulled it (`owner: <userId>`, `dicebearStyle`/`dicebearSeed` fields instead of `value`), by `POST /api/shop/avatar/randomize` (250 points, atomic guard, picks a random style from a curated "character" list plus a random seed, generates a whimsical two-word name like "Copper bot", auto-equips it) — past pulls stay owned forever and are re-equippable for free via `POST /api/shop/avatar/equip`. `User` gained `ownedCosmetics` (array of refs, spans all 4 types), `equippedCosmetics` (fixed `{background, border, theme}` object, each denormalizing `cosmeticId` **and** resolved `value` at equip-time so a page load never needs to `populate()`), plus **separate** avatar-equip fields `avatarStyle`/`avatarSeed`/`equippedAvatarCosmeticId` (an avatar needs a style+seed pair, which doesn't fit the single-`value`-per-slot shape the other three use). `controllers/shopController.js` (`/api/shop`) is now purely "what can I buy": `GET /items` (catalog filtered to `owner: null` — avatars never appear here), `POST /purchase`/`POST /equip` (background/border/theme only) and `POST /streak-freeze`, all atomic `findOneAndUpdate` guards with the `points >= cost` check *inside* the filter, not read-then-write. "Chapter/topic completion" points (+5, once per topic) piggyback on the existing lesson-view endpoint (`courseController.getTopic`) — `Progress` gained a `topicCompletedAt` field, atomically flipped from `null` so concurrent requests can't double-award. `utils/streak.js`'s `recordStreakActivity(userId)` is the one place `currentStreak`/`lastActivityDate`/`streakFreezeCount` change — called from quiz round-banking and topic-completion, never from a plain `GET /api/users/me`. Day-gap math uses **UTC calendar day** throughout — a documented simplification. Editor themes need no CodeMirror-level change: `playgroundHighlightStyle` (`src/main.js`) sources every token color from `--pg-*` CSS custom properties, so a theme cosmetic's `value` is a CSS class name (`editor-theme-sunset/ocean/forest/midnight`, in `src/tokens/colors.css`) applied directly to the editor mount `<div>` via `applyEquippedEditorTheme()`.
- **Badges — a real, automatically-awarded achievement system** (`models/Badge.js`, seeded via `scripts/seedBadges.js`/`npm run seed:badges`, 6 badges). `User.earnedBadges` is `[{badge, earnedAt}]`; `utils/badges.js#checkAndAwardBadges(userId)` checks all 6 criteria (First Steps: 1 topic completed; Bookworm: 25 topics; Week Warrior: 7-day streak; Quiz Master: reach `hard` band on any topic; Collector: own 5 cosmetics of any type; High Roller: 1,000 lifetime points) and is called after every points/streak/purchase/avatar-pull event. `User.lifetimePointsEarned` is a separate, never-decremented counter (only `utils/points.js#awardPoints()` touches it) specifically because `points` itself goes up *and down* with spending and can't answer "how much has this user ever earned."
- **Profile page (`/profile` route, `renderProfilePage()`) vs. Cosmetics page (`/cosmetics`, renamed from `/shop`, `renderCosmeticsPage()`).** The sidebar's old single "Shop" item is now two: "Cosmetics" and "Profile" — no sidebar streak-freeze widget (added, then explicitly asked to be removed again). **The Cosmetics page shows and equips all 4 cosmetic types, not just the 3 purchasable ones** — `GET /api/shop/items` now returns the buyable catalog (`owner: null`) *plus* the current user's own avatar pulls (`owner: userId, type: 'avatar'`, always `owned: true`, `pointsCost: 0`), merged into one `items` array, plus a `catalogSize` field (the purchasable-catalog count only, so "X of Y owned" stats can add owned avatars on top of that instead of pretending avatars are a fixed, finite catalog like the other 3 types). The page has tab filters (Everything/Avatars/Backgrounds/Borders/Editor themes), a search box, a top 3-card stats row (points to spend / cosmetics owned / currently-equipped avatar preview), and a "Randomise new avatar (250 pts)" button — avatar tiles there are equip-only (never purchasable, clicking calls `POST /api/shop/avatar/equip`, never `/purchase`). `handleAvatarRandomize()`/`handleAvatarEquip()` are shared between this page and Profile's Inventory (both invalidate both pages' caches and set both pages' error/notice state, so whichever is currently open shows the right feedback). New `controllers/profileController.js` + `routes/profileRoutes.js` (`/api/profile`): `GET /` aggregates the full owned-cosmetics list across all 4 types with equipped flags, the badge catalog with earned state, streak-freeze count, and account fields, in one call; `PUT /account` updates `name`/`bio`/three inert-for-now preference toggles (`dailyStreakReminder`, `showOnLeaderboard`, `soundEffectsEnabled` — no notification/leaderboard/sound system exists yet, these just persist); `DELETE /account` deletes the user, their `Progress` docs, and their owned (`owner: userId`) `Cosmetic` docs (global catalog cosmetics are untouched), then destroys the session same as logout. The Profile page's own Inventory still has three tabs (Cosmetics/Power-ups/Badges) rendered in a horizontally-scrolling row (`.inventory-scroll-row`, `overflow-x: auto` — deliberately not a wrapping grid), overlapping in content with the Cosmetics page's "Everything"/"Avatars" tabs by design (two views into the same owned-items data, not a bug). Deliberately **not built**: a "Settings" nav item (shown in an early mockup, never requested in text), leveling/XP (explicitly omitted), and email editing (the "university email" field in Account is read-only).
- **Toast notifications** (`showToast(message, {icon})`/`renderToasts()` in `src/main.js`) — a global stack rendered bottom-right, auto-dismissing after 4.5s, triggerable from any page that renders through `renderAppShell()`. Replaced the old per-page inline green "notice-text" success messages (shop purchases, avatar pulls, preference saves, points earned) with one consistent pattern; scoped to **success** messages only — inline `error-text` (a real, page-scoped `xError` string variable, e.g. `languagesPageError`, `profilePageError`) is still the convention for failures, not toasts.
- **Home/Dashboard page (`/` route, full rewrite of the former placeholder `renderDashboardPage()`).** New `GET /api/home` (`controllers/homeController.js`) aggregates everything in one call, same pattern as `/api/profile`: real streak/points/topics-done stats (no XP/leveling — explicitly ruled out, twice), a **real, persisted daily goal** (`User.dailyGoalTier`: chill/steady/serious → 1/2/4 topics/day, replacing the old client-only unsaved `selectedGoal` radio on the onboarding/languages pages — now saved through the existing `PUT /api/users/me` alongside `languagesToLearn`), a **"pick up where you left off" card** backed by a new `User.lastViewedTopic` field (unconditionally overwritten on every `courseController.getTopic` call, not just first-time completions — previously nothing server-side remembered this, only lost-on-refresh client state), and a **weekly activity calendar** backed by a new `User.dailyActivityLog` array (`[{date, pointsEarned, topicsCompleted}]`, capped to the last 14 entries) that also answers "points this week" and "streak increased today" from the same data instead of separate ad-hoc counters. `utils/streak.js` was renamed `utils/activity.js` and its `recordStreakActivity(userId)` became `recordActivity(userId, {pointsEarned, completedTopic})` — same two call sites as before (quiz round-banking, topic-completion) — since the streak logic and the new daily-log update always fire together. Per-language "My tracks" progress cards compute "Chapter X of Y" from the chapter of the *most recently completed* topic in that language (or "Not started"), and a chapter-scoped progress % (not a fabricated per-topic percentage). The mockup's "3 questions · 1 code exercise" meta line only kept the question count (`Question.countDocuments`, real but reads 0 until question-bank population happens) — there's no "code exercise" concept anywhere to source honestly, so it was dropped rather than faked. Deliberately **not built** here either (at the time): the mockup's sidebar changes (an old screenshot, not a request — kept the sidebar exactly as-is: Cosmetics/Profile naming, no Settings, no sidebar streak-freeze widget). Rankings was added to the sidebar later — see the Leaderboard bullet below.
- **Gotcha: removing `unique: true` from a Mongoose schema field does NOT drop the index already sitting in MongoDB.** `Cosmetic.name` was `unique` when it only held a small fixed catalog; once avatar pulls (randomly-generated two-word names, unbounded, per-user) started sharing the same collection, two different users' pulls could land on the same name and hit a live `E11000 duplicate key` error at write time even though the *schema* no longer declared `unique`. Fixed by running `Cosmetic.syncIndexes()` once to actually drop the stale `name_1` index from the database — schema changes to indexes always need this (or an equivalent manual `dropIndex`) to take effect on an existing collection; `npm run seed`-style upserts never trigger it themselves.
- **Phase 9 (Leaderboard/Rankings) — a new phase inserted into the plan and built 2026-08-29, sequenced *before* Phase 10 (UI Polish, renumbered up from the old Phase 9) so the new page still gets covered by that phase's final pass.** `/rankings` route, `renderRankingsPage()` in `src/main.js`, sidebar entry with a new `icons.trophy` glyph between "Quiz collection" and "Playground". An earlier My course/Friends/Everyone scope-tab design was dropped before build in favor of one platform-wide ranking plus a **metric pill** (Points / Streaks / Quizzes done, reusing `.filter-pill`) that swaps what the table is sorted by, alongside a period tab row (This week / This month / All time). New `GET /api/leaderboard?metric=&period=` (`controllers/leaderboardController.js` + `routes/leaderboardRoutes.js`) computes rankings live via `User.find()` + an in-memory sort — no denormalized leaderboard collection. Points/quizzes-done "this period" reuse `User.dailyActivityLog` rather than a new ledger: the log's cap was bumped from 14 to 31 entries (`utils/activity.js`) so a rolling 30-day window has enough history for "This month," and entries gained a `quizzesFinished` field (incremented by `recordActivity(userId, { quizFinished: true })`, called from `quizController`'s existing round-banking call site alongside `pointsEarned`). `User` gained `lifetimeQuizzesFinished` (mirrors `lifetimePointsEarned`) to back the "All time" view without summing the capped log. "This week"/"This month" are a **rolling** N-day window computed on read, not a real calendar-week/month reset — no scheduler was built, matching the same simplification `homeController`'s `pointsThisWeek` already made. **Streaks always show the live `User.currentStreak`**, identical across all three period tabs by design — a streak has no historical "sum" to window. **Rank movement (↑/↓ vs. the previous period) is only computed for period=week** (diffed from the same 31-entry log, no snapshot table needed) — it's `null` (rendered as "—") for This month (would need 60 days of history against a 31-entry cap) and for the Streaks metric (a live value has no distinct "previous period"). The existing (previously inert) Profile `showOnLeaderboard` toggle is now live: `getLeaderboard` queries `{ $or: [{ showOnLeaderboard: { $ne: false } }, { _id: currentUserId }] }`, so an opted-out user is excluded from everyone else's view but still sees their own row/rank in their own. Only a minimal mobile breakpoint was added (hides the Streak/Quizzes columns under 700px); a fuller responsive pass is left to Phase 10 like the rest of the app. See [PROJECT_PLAN.md](PROJECT_PLAN.md)'s Phase 9 for the full list of design decisions made.

**Phase 10 (UI polish) — first real mobile-responsive pass done 2026-08-28**, found by testing the deployed build on an actual phone rather than just resizing a desktop browser. Two of the fixes are genuinely reusable CSS gotchas, not one-off page bugs:
- **A `display: none` rule declared outside a media query silently wins over an `opacity`/`visibility` toggle declared inside one, even when the inner rule's class is applied.** `.sidebar-overlay` had an unconditional `display: none` (meant only for desktop, where there's no mobile menu) sitting above the `@media (max-width: 768px)` block that toggled `opacity`/`visibility` via `.overlay-open` — since the media-query version never re-declared `display`, the overlay was invisible and unclickable at every viewport width, not just desktop. "Click outside the mobile sidebar to close it" silently did nothing as a result. Fixed by adding `display: block` inside the media-query rule. Check for this same split-declaration pattern before assuming an `opacity`/`visibility` toggle alone is sufficient anywhere else in this stylesheet.
- **`align-items` on a flex container governs the CROSS axis, which flips from vertical to horizontal the moment `flex-direction` switches to `column` at a breakpoint — a non-`stretch` value left over from the row layout silently stops children from filling the container's width.** `.lesson-layout` switches to `flex-direction: column` below 900px but never overrode its `align-items: flex-start` (meant for the desktop row layout), so `.lesson-main` sized itself to its own max-content width (as if none of its prose text were allowed to wrap) instead of stretching to the viewport — a real, significant horizontal page overflow with no single obviously-wide element to blame, since every child was just inheriting the same oversized parent. Fixed by adding `align-items: stretch` inside that breakpoint. Any future `flex-direction: column` breakpoint override needs to make the same check.

Smaller mobile fixes from the same pass, worth knowing exist but not worth their own gotcha writeup: the mobile sidebar used `height: 100vh` (taller than what's actually visible once a mobile browser's address bar is showing, cutting off the bottom nav items) — switched to `100dvh` with `100vh` kept as a fallback; the mini playground's header row (icon/title/filename/reset/expand/run/close, all in one line) could overflow at narrow widths with the close button — last in the row — silently clipped off since the panel hides overflow, fixed by guaranteeing the buttons `flex-shrink: 0` and letting the title/filename text shrink or hide instead; the auth page's absolutely-positioned topbar pill could overlap "Create your account" (a longer heading than "Welcome back") — fixed by top-aligning with reserved clearance instead of vertically centering on narrow screens; the onboarding "First-time setup" chip and the "Go to my dashboard" button both had layouts that only worked with short content/wide screens and needed breakpoint-specific repositioning (chip moves below the topbar's divider line on mobile; the dashboard button drops onto its own full-width line below the topics-unlocked count instead of squeezing beside it). The Profile page had its own earlier round of similar fixes (a `.profile-top-row` mobile-collapse media query that was dead code due to cascade ordering, and a flex `min-width: 0` gap on the account-email row) — see git history around 2026-08-28 for the full diff if a similar bug resurfaces elsewhere.

**Express version note**: this project is on Express 5, which dropped bare `app.get('*', ...)` wildcard routes (path-to-regexp v6+). The SPA fallback in `server.js` uses a path-less `app.use((req, res) => ...)` instead — keep that pattern for any future catch-all routes.

Key sequencing/design notes from the plan (don't relitigate these without reason):
- Phase 6 deliberately builds a genuinely **adaptive** engine, not a fixed set of named difficulty-tier quizzes — an early design pass considered a fixed-tier UI (separate "Chill/Steady/Serious" quizzes with best-score/retake tracking) but that was rejected specifically because the project's own plan titles this phase "Adaptive," and a fixed-tier model can't represent a per-topic band that changes question-to-question. Don't reintroduce discrete named quizzes without revisiting this.
- Phase 4 (course content) and 5 (in-browser code editor) needed their own schema/design decisions made explicitly before implementation — the plan lists open questions for each (e.g. Markdown vs. typed content blocks for chapters) rather than prescribing an answer. Any future phase's open questions should be surfaced as decisions to confirm with the user rather than picked silently, the same way Phase 6's adaptive-vs-fixed-tier call and its band-transition/points-penalty formulas were worked out.
- Phase 5 (sandboxed code execution, e.g. via Judge0) was flagged as the highest-risk/most time-uncertain phase; it's built now (see Playground above).
- Phases 4–6 carry the most grading weight — don't let auth/profile/polish work crowd out time budgeted there.
- Cosmetics/inventory (Phase 8) intentionally isn't pre-declared on the `User` schema yet — Mongoose/MongoDB documents don't need the field to exist upfront, so add it when that phase is actually built rather than now.

## Commands

Inside `codepilot/`:
- `npm run dev` — start the Vite dev server (frontend only, hot reload)
- `npm run build` — production build to `dist/`
- `npm run preview` — preview the production build via Vite
- `npm start` — run the Express server (`node server.js`); requires `dist/` to already exist (run `build` first) and `MONGO_URI` in `.env` to point at a reachable MongoDB instance, since `connectDB()` blocks server startup until it connects
- `npm run seed` — upsert course content from `scripts/seedChapters.js` into MongoDB; safe to re-run
- `npm run seed:questions` — parses `.md` files from `scripts/question-content/` and upserts the quiz question bank into MongoDB; safe to re-run; requires `npm run seed` to have run first (it looks up real topic `_id`s from the already-seeded chapters). See the `scripts/seedQuestions.js` bullet above for the file naming/format convention. All 66 topics across all 13 JavaScript chapters have real questions seeded (1,980 total) — every other language still has zero.
- `npm run seed:cosmetics` — upsert the Phase 8 shop's cosmetic catalog from `scripts/seedCosmetics.js` into MongoDB; safe to re-run (upserts by `name`); no dependency on `seed`/`seed:questions` having run first. Only seeds the 3 global-catalog types (background/border/theme) — avatar-type `Cosmetic` docs are created dynamically per user pull, never by this script.
- `npm run seed:badges` — upsert the 6-badge achievement catalog from `scripts/seedBadges.js` into MongoDB; safe to re-run (upserts by `name`); no dependency on any other seed script.

`.env` (gitignored) needs `MONGO_URI`, `SESSION_SECRET`, `PORT`, `JUDGE0_API_KEY`, `JUDGE0_HOST` (RapidAPI Judge0 CE — free tier, ~50 executions/day). No test runner, linter, or formatter is configured yet. When those are added, update this file with the actual commands rather than assuming a convention.
